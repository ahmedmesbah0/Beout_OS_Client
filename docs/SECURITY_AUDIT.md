# Beout_OS Security Audit & Threat Model Report
This document provides a comprehensive security review of the Beout_OS client appliance and the central management server.

---

## 1. Threat Model (STRIDE)

### Client Appliance (VM)
* **Spoofing**: Threat of an activated VM spoofing another VM's machine-id. 
  * *Mitigation*: The activation token is an Ed25519 signature of the unique `/etc/machine-id`. Bypassing this signature check requires the private key of the main server.
* **Tampering**: Threat of altering local SQLite database parameters (e.g., manually setting `activation_status` to `ACTIVE`).
  * *Mitigation*: The daemon continuously validates the signature (`activation_token`) of `/etc/machine-id` using the public key. If the signature doesn't match, status resets to `INACTIVE`.
* **Repudiation**: Threat of a client denying check-ins.
  * *Mitigation*: The background updater records pings with IP address, version, and license key on the central server database.
* **Information Disclosure**: Threat of exposing the web session token or network configurations.
  * *Mitigation*: Web sessions are held in-memory; config-engine access is restricted by local system group permissions.
* **Denial of Service**: Threat of flood attacks on the C++ local API server (`beout_os_api` on port 8080/8443).
  * *Mitigation*: The daemon binds strictly to localhost or the designated MGMT interface, preventing external WAN traffic access.
* **Elevation of Privilege**: Threat of the web panel executing commands as root.
  * *Mitigation*: C++ daemon runs as a restricted service user; scripts use narrow `sudoers` configurations for network reconfiguration.

### Central Management Server (PHP)
* **Spoofing**: Threat of fake check-ins.
  * *Mitigation*: The server validates license keys against SQLite records before returning status updates.
* **Tampering**: SQL injection into licensing tables.
  * *Mitigation*: Prepared statements (PDO parameter binding) are used across all SQL queries.
* **Elevation of Privilege**: Remote code execution via file upload.
  * *Mitigation*: The update publisher accepts only `.deb` files, validates them, and stores them under a sanitized versioned filename structure.

## 2. Attack Surface Analysis
* **Local Console (CLI)**: Interactive configuration console prompts for network options. Restricted to root or local console.
* **REST APIs (C++ Daemon)**: Binds to `0.0.0.0` or custom MGMT port. Listens for configuration and licensing POST/GET requests.
* **Central Server PHP APIs**: Public endpoints `/api/license/activate` and `/api/license/heartbeat` are exposed to the internet. 

---

## 3. Input Validation Review
* **Network Parameters**: The C++ setup engine validates IP addresses, netmasks, and gateways using regular expressions:
  * IPv4 Regex: `^(?:[0-9]{1,3}\.){3}[0-9]{1,3}$`
* **JSON Payloads**: The C++ API server parses incoming requests using `nlohmann::json`, wrapped in `try/catch` blocks to prevent daemon crashes due to malformed payloads.

---

## 4. Memory Safety Review
* **C++ Memory Safety**: The daemon avoids raw pointer management, utilizing `std::unique_ptr` and `std::shared_ptr`.
* **String Buffers**: Replaced fixed character arrays with `std::string` and `std::stringstream` to eliminate buffer overflow risks.

---

## 5. Authentication Review
* **Web UI Session**: The client dashboard utilizes JWT-like Bearer tokens generated by the daemon at login. Tokens are kept in-memory.
* **Server Inter-communication**: Heartbeats and activations are authenticated via cryptographic token signatures verified using the embedded public key.

---

## 6. Authorization Review
* **Client Admin API**: Endpoints check the `Authorization` header. Unauthorized calls return `401 Unauthorized`.
* **Server Admin Panel**: Access is restricted based on hosting environment configurations (e.g., htaccess, IP restriction, or session checks).

---

## 7. Filesystem Review
* **Database File**: `/var/lib/beout_os/config.db` permissions are locked to `0600`, owned by the service user.
* **Public Key**: `/opt/beout_os/etc/license_public_key.pem` is read-only for client validation pings.

---

## 8. Logging Review
* **VM Logging**: Network changes, manual triggers, and updates are logged to standard syslog via `<syslog.h>`.
* **Server Logging**: Web traffic pings are captured by Nginx/Apache logs, and heartbeat state updates are recorded in SQLite timestamps.

---

## 9. Error Handling Review
* **API Failures**: Clients catch exceptions gracefully and return structured JSON error payloads (e.g. `{"error": "Failed to connect to license server"}`).
* **Server Errors**: PHP script uses explicit try-catch blocks to prevent raw database exception traces from leaking inside HTTP responses.

---

## 10. Configuration Review
* **Default Fallback Key**: The default public key fallback inside the client API is used if the PEM file is missing, ensuring cryptographic checks cannot be bypassed by deleting the key file.
